# 1.0 — Fundação de autenticação, sessão e shell da aplicação

**Módulo:** M1 · **Projeto Linear:** 1.0, 1.1.3, 1.4, 8.4 (base técnica) · **Prioridade:** Essencial · **Ordem:** 1 (bloqueia todas as demais)
**UCs:** UC004, UC012 (base) · **RF:** RF01, RF21 · **RNF:** RNF01, RNF04, RNF10, RNF11, RNF14, RNF19, RNF21, RNF24, RNF26, RNF31
**Telas:** 01, 02, 03, 04, 05 (mínima), 16, 18, 19, 20, 21 (esqueleto de rotas e layout)
**Camadas:** Arquiteto (decisões) → Back-end (Controller/Model) → Front-end (View) → DevOps (seed/env) → QA

## História
**Como** equipe de desenvolvimento, **quero** a infraestrutura comum de autenticação (JWT, hash de senha, rate limiting, erros padronizados, rotas protegidas e layout responsivo) **para que** todas as histórias do M1 e dos módulos seguintes se apoiem em uma base única e segura.

## Escopo
**API**
- Middleware de autenticação por JWT com prazo de validade (RNF01) e middleware `exigirAutenticacao` que carrega o usuário e a Casa/papel dele.
- Hash de senha com bcrypt (RNF02); nenhuma senha ou código em texto puro em banco ou log.
- Rate limiting nas rotas públicas de `/auth/*` (RNF14), respondendo `429 MUITAS_TENTATIVAS`.
- Formato único de erro com **código fixo** (ex.: `CREDENCIAIS_INVALIDAS`, `EMAIL_EM_USO`, `DADOS_INVALIDOS`, `SENHA_INCORRETA`, `CODIGO_INVALIDO`, `CONTA_NAO_ENCONTRADA`, `MUITAS_TENTATIVAS`) — o front usa o código para escolher a mensagem.
- Validação Zod em todo endpoint (schema em `auth.schema.ts`, contrato de referência para o front).
- Serviço de e-mail (Mailpit em dev) com template de código de 6 dígitos.
- Seed do catálogo de planos (INDIVIDUAL, FAMILIA, BUSINESS) necessário para criar a Casa no cadastro.
- `GET /me`: dados do usuário logado + Casa + papel + plano vigente (alimenta as telas 05, 16 e 20; não consta na Tabela 17, ver decisões).

**Front-end**
- Rotas públicas (01, 02, 03, 04, 18, termos) e rotas protegidas (05, 16, 19, 20, 21) no React Router, conforme o diagrama de processos (5.7).
- Guarda de rota: sem token válido, rota protegida redireciona para 02; com token válido, rota pública redireciona para 05.
- Cliente HTTP com injeção do token, tratamento de 401 (limpa sessão e vai para 02) e mapeamento código de erro → mensagem em português.
- Tokens de design da Tabela 3 do protótipo (verde #0F5C4D, âmbar #E9A23B, fundo #F6F5F1, vermelho #C2412D, Inter) no Tailwind.
- Layout autenticado mínimo: barra inferior no celular e menu lateral no desktop, com as entradas Início e Conta ativas (demais entradas desabilitadas/ocultas até seus módulos existirem).
- Tela 05 **mínima** (saudação, nome da Casa, papel): o conteúdo real do Início é M4.
- Banner de falta de conexão (RNF24): "Sem conexão com a internet", sem travar a tela.

## Critérios de aceite
1. **Dado** uma rota protegida da API, **quando** chamada sem token, com token inválido ou expirado, **então** responde 401 com código de erro e nenhum dado é retornado.
2. **Dado** um visitante sem sessão, **quando** acessa `/conta` (tela 16) pela URL, **então** é redirecionado para a tela 02.
3. **Dado** um usuário com sessão válida, **quando** acessa `/entrar` ou `/criar-conta`, **então** é redirecionado para a tela 05.
4. **Dado** mais requisições às rotas públicas de `/auth/*` do que o limite configurado em uma janela, **quando** excede, **então** a API responde 429 `MUITAS_TENTATIVAS` e o front exibe mensagem amigável.
5. **Dado** a falta de conexão, **quando** qualquer tela pública ou privada tenta chamar a API, **então** aparece a mensagem de falta de conexão e a aplicação continua utilizável (RNF24).
6. **Dado** qualquer erro da API, **quando** o front o recebe, **então** exibe mensagem clara em português escolhida pelo código do erro, nunca o texto técnico cru.
7. **Dado** um banco novo, **quando** a migration e o seed rodam, **então** os três planos existem (necessário ao UC008).
8. **Dado** as telas da sprint, **quando** abertas em 360 px, 768 px e 1440 px, **então** o layout se adapta sem rolagem horizontal (RNF10), todos os campos e botões têm rótulo acessível (RNF19).
9. **Dado** a regra de camadas do MVC, **quando** o código é revisado, **então** controller não contém regra de negócio, service não conhece HTTP e a View não contém regra nem acessa banco.

## Regras de negócio
- Senha só como hash bcrypt; JWT com expiração; segredos só em variáveis de ambiente.
- Permissão vale na API (RNF31); esconder botão na tela é só complemento.
- Toda rota, exceto as de visitante (`/auth/cadastro`, `/auth/login`, `/auth/recuperar-senha`, `/auth/redefinir-senha`) e a da rotina (`/internal/jobs`), exige token.
- Todo usuário sempre pertence a uma Casa (cada usuário participa de uma Casa por vez).

## Definition of Done
Lint e typecheck passando, testes de middleware/erros/guardas passando, critérios 1–9 verificados pelo QA, revisão do AppSec nos itens de JWT, hash e rate limiting.
